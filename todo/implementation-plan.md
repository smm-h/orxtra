## Conventions applying to every item

- "Green" = affected module suites + root `tests/` pass, ruff (select=ALL) passes,
  per-module mypy --strict passes, `scripts/check_imports.py` passes. Until Phase 0.1
  lands, run `uv sync --reinstall-package orxtra` after source edits (the venv otherwise
  serves stale hardlinked snapshots).
- One `safegit commit` per item for hand-written changes; `rlsbl commit` (or bare
  `selfdoc gen`) for machine-generated artifacts (Autogenerated trailer); an
  `rlsbl changelog add` entry per commit group, as work proceeds — never backfilled.
- Red-green for every bug fix: failing test first, then fix, then green.
- Verification criteria are definitions-of-done, not suggestions.

**3.2 The http execution type.**
Call-time definition-level secret substitution (values never in the Tool object or
LLM-visible text); URL-encoded interpolation with mandatory patterns for interpolated
params; enforced output validation. Effect tags derived from HTTP method.
Verify: red-green — sentinel never in text/data/trace; missing declared output field
fails; POST tool carries mutation tag, GET-only readonly.

**3.3 The monty execution type.**

functions, each capability the corresponding built-in through the shared pipeline core.
The command capability relocates the existing subprocess machinery as its backend. 
Explicit ResourceLimits (required); ToolError propagation via exception injection;
capability-derived tags.
Verify: e2e — file capability writes through write-safety (stale-tracking observable),
traced; command capability runs a pinned executable with arg validation, traced;
infinite loop dies at declared limit; ungranted capability hard-errors; readonly-only
grants yield readonly tag.

## Dependency structure and parallelization

Trunk: 0 → 1 → 2 → 4 → 5. Branches: 3 off 0 (parallel with 1–2); 6 off 0 with 3.4
before 6.2 and 6.3; 7 needs 0.6 + 3, and 7.1's agent-TOML surface additionally waits
for 6.2; 8 needs 3 + 7.1; 9 needs everything.

Three concurrent sessions after Phase 0 (Phase 0 itself is sequential single-session;
within it, 0.4 lands before 3.1 later extends RunConfig). Sessions share ONE worktree:
the ownership matrix is file-level, and "rebase" means WAIT for the other session's
commits to land before touching a shared file — hard handoff points, no merge
resolution.

- Session 1 (phases 1→2→4→5) owns: schema/, trace/, dispatch/, auth/, api/, incoming/,
  cli/ (db + dispatch groups), tests/pg_fixtures.py, migration baselines. Priority owner
  of services/.
- Session 2 (phases 3→7) owns: tool/, agent/ types+loader (during 3.4 only),
  scheduler tool-registry/allow-resolver/agent-tools files, worker/ tool building,
  examples/, tests/test_e2e_security.py. Hands the agent loader to Session 3 after 3.4;
  takes it back for 7.1 only after 6.2 lands.
- Session 3 (phase 6) owns: compose/, agent/ _prompt+loader (post-3.4), scheduler
  prompt-assembly files, overseer/_knowledge, notepad/_reader. Waits for 3.4 before
  6.2/6.3; waits for Session 1's services items before 6.4.

Fallback if shared-worktree coordination proves fragile: run the three tracks
sequentially (S1, then S2, then S3) — slower, zero coordination risk.

  land the data-scrub in both pipelines with the drift-sentinel test in Phase 0, and do
